# JRXML Web Designer

A browser-based visual designer for JasperReports JRXML templates, built with Vue 3 + TypeScript + Vite.

## Core Architecture

This is a **bidirectional JRXML designer**. The entire application revolves around three critical data transformations:

```
UI (Vue Canvas) ⇄ Structured JSON ⇄ JRXML (XML)
```

### Critical Path 1: JSON → JRXML (Generation)

- **Entry**: `src/utils/jrxmlGenerator.ts` → `generateJRXMLContent()`
- **XML header**: `src/utils/jrxml/xmlBuilder.ts` → `buildJasperReportOpenTag()`
- **Types**: `src/utils/jrxml/types.ts` (`ReportProperties`, `Field`, `Parameter`)
- Flattens the visual JSON model into JasperReports-compatible XML
- Handles all element types: textField, image, line, rectangle, ellipse, frame, table, chart, barcode. Designer pages are written as detail bands separated by `<break type="Page">`

### Critical Path 2: JRXML → JSON (Parsing)

- **Entry**: `src/utils/jrxml/parse.ts` → `parseJRXMLContent()`
- Uses browser `DOMParser` to parse XML
- Extracts: `properties`, `bands`, `fields`, `parameters`, `datasets`, `variables`, `styles`
- `<staticText>` is read as a Text element (`textField` with a quoted literal expression); `<break>` only splits detail pages and is never kept; an `<image>` carrying `com.cdp.chart.binding` is read as a Chart; subreport, list, crosstab, map, icon label, sort and generic elements and native JasperReports charts (`<pieChart>`…) are not supported and are dropped on import, as is the `<summary>` section; `<title>` is read as the cover page (below)
- Handles multiple namespace resolution strategies (direct children, namespace-aware, localName)

### Critical Path 3: JSON → UI Binding (Designer Canvas)

- **Main component**: `src/components/PDFDesigner.vue` — the core orchestrator
- The JSON model (`reportProperties`, `bands`, `reportFields`, etc.), its JRXML (`jrxmlContent`, written by `updateJrxml()`) and undo/redo live in the Pinia store `useReportStore` (`src/stores/report.ts`); `PDFDesigner.vue`, the canvas and the panels read them from the store, and the designer calls `reportStore.reset()` when it opens (a fresh report each visit)
- Elements rendered in `src/components/designer/` sub-components
- Drag/drop, resize, selection all operate on the JSON model directly
- Changes to JSON immediately reflect in the visual canvas

### Round-Trip Integrity

The most important invariant: **edit in designer → export JRXML → re-import → should produce identical visual result**. Any bug in parse/generate/bind breaks this.

## JSON Data Model

The central data structures live in `src/types/index.ts`:

- `ReportProperties` — page size, margins, default font
- `Band` — layout region (detail, pageHeader, columnHeader, background…) containing elements; no title or summary band (the cover page is written as `<title>`, see "Cover and contents pages")
- `DesignElement` — union of `TextFieldElement | ImageElement | LineElement | RectangleElement | EllipseElement | FrameElement | TableElement | ChartElement | BarcodeElement | CustomTableElement` (the element library offers exactly these, plus the Element Presets, Page Border and Page Number)
- `Field`, `ReportParameter`, `ReportVariable` — data model definitions
- `ReportStyle`, `ConditionalStyle` — style system

## Frames, Cards and Page Border

Logic lives in `src/utils/framePresets.ts`: border presets, per-side pen helpers, the library templates ("Element Presets": Number Box, Alert Box, Section Box, Photo Box; Page Border is under "Composite Elements"), and fitting a box's children when it is resized. The plain Box tile (Basic Elements, a `frame`) lets users build their own boxes; parts work the same in it.

- **Stacking**: hovering never raises an element, and a selected part inside a box keeps its place in the box's order (raising hid what lies on top, e.g. a cover's texts on its colour panel).
- **Dropping on top**: a library element dropped over another goes on top of it (into the box under its centre, after the box's parts, else into the band). An image only takes picture files dropped from the computer (`isFileDrag` in `ImageElement.vue`); every other drag passes through it to the page.
- **Box parts**: the items a template builds (label, number, photo…) carry the `com.cdp.box.part` JRXML property (`isBoxPart`). Only these are kept inside their box when dragged, resized, nudged or typed; items the user drops into a box move freely. Parts act as a group, like PowerPoint (`FrameElement.vue`): dragging a part moves the whole box unless that part is already selected; a click on a part selects the box first, a second click the part; a right-click on a part opens the box's menu unless that part is already selected. Right-click on an item inside a box shows exactly one of "Add to box" (dropped-in item → part, `markBoxPart`) or "Move out of box" (part → ordinary item in the band, `releaseBoxPart`).

- **Element Presets sub-groups**: the library shows Element Presets in small titled groups (`group` on the registry entry, `elementLibrary.presetGroups.*`): Boxes (the templates above), Header & Footer, Headings & Text, Status, Sign-off, Tables.
- **Table presets** (`utils/tablePresets.ts`, group Tables): Key Statistics, Financial Summary, Progress Table, Comparison Table (two header rows), Action Plan, Risk Register. Each is an ordinary typed table (Corporate Blue, full width, placeholder text, merges, header / total rows, bullet-point cells), added through the report-part path (`REPORT_PART_TYPES` includes `TABLE_PRESET_TYPES`). A status is a coloured "●" (U+25CF) in its cell, changed with the cell's text colour; the server's Noto Sans SC has the glyph (checked with the font file in a fill; Helvetica, the PDF fallback, does not).
- **Report parts** (`utils/reportParts.ts`, the presets taken from a monthly project report): Report Header (dark banner, grey bars, three title lines), Page Footer (line, "Page X of N", logo spot), Section Heading, Sub-heading, Note, Risk Legend, Status Dot, Sign-off. Boxes with parts, or single elements. Clicking the Header / Footer tile puts it in the Page Header / Page Footer (a message if that band is off); dragging drops it anywhere. Circles get Status colour quick picks (green / amber / red) in Basic Properties. Text boxes are at least ~1.45 × the font size tall: JasperReports drops text whose first line doesn't fit in Noto Sans SC.
- **Page border** = a frame in the Background band, sized to the printable area. Only one is allowed (`findPageBorder`): the library tile is disabled once it exists, and add/paste show a warning and select the existing one. While the tile is dragged over the page, the whole printable area (the Background band) is highlighted as the drop target, never the band under the pointer. On the canvas the Background band is drawn over the bands (`mix-blend-mode: multiply`) and ignores the mouse, except a thin strip along the border line so it can be clicked. The Background band is never counted in band-height totals, and `<background>` is always written first.
- **Borders are pens only** (`box.pen` / `topPen`…); fills are a separate feature. The Basic tab shows presets only; per-side editing is the Style Settings side-border controls.
- **Rounded frames**: JasperReports can't round a frame border, so the generator writes marked rounded rectangles as the frame's first children, and the parser turns them back into the frame (`ROUNDED_BORDER_PROPERTY` marker, exact pens in `ROUNDED_BORDER_PENS_PROPERTY`):
  - `radius` + the same line on all sides → one rounded rectangle carrying the pen and fill
  - `radius` + a partial border (accents) → two stacked filled rounded rectangles (border colour behind, inside colour in front, inset by each side's width); solid, one colour, inside filled
  Canvas and generator share the same helpers (`getLayeredBorder`) so they always match. No SVG or images.
- **Corner radius per corner** (boxes, images and text, Style Settings: "All corners" + one field per corner): stored in CSS order ("12 0 6 0"), one value when all match. Boxes: all equal → `radius` (rounded rectangle above, rounded in the PDF); different → `cornerRadii`, written as the `com.cdp.box.cornerRadius` frame property. Images: always the `com.cdp.image.cornerRadius` property; text fields (page numbers included): always `com.cdp.text.cornerRadius`. JasperReports has one radius per rectangle and none on images or text fields, so the canvas draws these and the report server is expected to read the properties.
- **Image shapes** (Basic tab → Shape: Square, Rounded, Soft, Circle, Pill, Leaf, Top round, Drop; `IMAGE_SHAPES` in `utils/elementUtils.ts`): stored as `com.cdp.image.shape`, each corner a share of the image's short side, so the shape follows resizing. Choosing a shape never changes the image's size: Circle and Pill both round it fully (a circle on a square image, a pill on a wide one). The generator always writes the pixel radii for the current size into `com.cdp.image.cornerRadius` (`reportElementProperties`). Typing a corner in Style Settings drops the shape (Custom).

## Cover and contents pages

Pages at the front of a report with **no shared sections** (page header, column header, column footer, page footer; the page border still prints on them, except on a whole-sheet cover) that use the **whole printable page** (report margins kept). A new report has neither. Logic in `utils/specialPages.ts`; settings `ReportProperties.coverPage`, `contentsPages` (count) and `countSpecialPages` (false only), written as the report property `com.cdp.specialPages`.

- **In the designer** they are ordinary Detail pages (elements with `pageIndex`): the cover is page 0, the contents pages follow, then the normal pages (always at least one; `report.totalPages` includes them). `pageKind` / `isSpecialPage` say which a page is. The canvas (`DesignerCanvas.vue`) draws them as one area of the printable height with a badge ("Cover page", "Contents page 2"), without the shared bands or the Background layer.
- **Adding and changing**: "Add cover page" / "Add contents page" (top left of the first page while missing), "Add contents page" on the last contents page, and the ⋯ page menu: "Make this the cover page" (page 1 of a report without either), "Make this a contents page" (the first normal page), "Turn into a normal page" (the cover when there are no contents pages; the last contents page), "Delete". Content stays when a page changes kind; the only normal page turned special gets a new normal page after it. One undo step each (`handlePageAction`, `deletePage` in `PDFDesigner.vue`). Normal pages are always added after the special ones.
- **Not allowed on them** (refused with a message on drop, drag, paste, click-add and when changing a page's kind; `specialPageProblem(element, pageKind)`): page numbers (also inside a box) and project-data tables; on the cover also a Contents List.
- **Boxes are per page**: a drop or drag lands in a box only when the box is on the same Detail page (a cover design is one page-sized box; matching boxes on other pages put items on the cover). Contents Lists never go in a box. Items may use the whole page: drop fitting, nudging, resizing, fit-to-text and the out-of-bounds check use the printable height there (`bandAreaHeight`).
- **JRXML** (checked in a JasperReports fill): the cover is the `<title>` band, printable height, `splitType="Prevent"`, with `isTitleNewPage="true"`. Each contents page is a frame of the whole printable area in `<background>` (marked `com.cdp.contentsPage` = its number) with `printWhenExpression` `$V{PAGE_NUMBER} == n`, plus an empty Detail band holding its page. The shared bands get `$V{PAGE_NUMBER} > N`. The other background items (the page border) print on every page, cover and contents pages included, except a whole-sheet cover (a border dropped on a whole-sheet cover is refused with a message; dropped on another page or added by click it is added with a note that the cover has none) (`guardPrintWhen(1, …)`, their own rule kept inside; `unguardPrintWhen` reads it back); the canvas shows them the same way. The parser turns `<title>` (also from other tools) into the cover and the marked frames into contents pages, and moves the Detail pages after them.
- A contents page never grows: its content must fit the page (out-of-bounds shows what doesn't).
- **Whole-sheet cover** (`fullPageCover`; ticked by default in the cover design picker, switched in the cover's ⋯ menu; the cover's content is then fitted to its new area in proportion, `scaleElementsToArea` in `utils/pageFit.ts`, text keeping its height): the cover is drawn and designed edge to edge (`specialPageArea` gives the page area: the sheet for this cover, else the printable page; canvas, drop fitting, out-of-bounds and page fitting use it) and its elements are placed from the sheet's corner. JasperReports allows negative x / y but no element below its band, so the JRXML is written with `bottomMargin="0"`, the cover's elements shifted by the left / top margins, and the bottom margin's space added to the page footer and last page footer (an empty guarded page footer when there is none); the real margin is kept in `com.cdp.specialPages` and the parser undoes all of it (reading the cover's negative positions from the band). Normal pages print exactly as before (checked element by element in a fill). Designs built for the sheet keep text and logos `inset` from the edge.
- **Designs** (`utils/pageDesigns.ts`): "Add cover page" / "Add contents page" and the page's **Change design** button (on every cover / contents page) open `DesignChooserModal` (Blank + 5 cover designs: Photo + side panel, Full photo, Minimal, Colour block, Project card; + 4 contents designs: Classic, Dotted lines, Numbered boxes, Two columns), with previews drawn by `common/DesignThumbnail.vue`. A cover design is one box of the printable size holding its parts (photos, colour blocks, logo spot, texts); a contents design is a heading plus one or two Contents lists. Choosing a design for a page with content asks first and replaces it; one undo step. Element Presets has two groups: **Cover Pages** (the 5 cover designs) and **Contents Pages** (the 4 contents designs; the Contents List itself is a Basic Element). A design tile (click or drop) sets that page's design through the same path (`applyDesignFromLibrary`): a cover design goes on the cover, a contents design on the contents page it was dropped on (else the first one); the page is added when missing, its content replaced after asking. Contents designs have their heading and accent line centred and their lists centred on the page; Blank in the picker is the start of a page of one's own.
- **Contents list** (`contentsList` element, `utils/contentsList.ts`, `jrxml/contentsListXml.ts`, `elements/ContentsListElement.vue`, `properties/ContentsListProperties.vue`): rows of number, title and page (`ContentsListData`: entries with level 0 = section / 1 = indented sub-section, row height, text size, number and page column widths, dotted leader, bold sections, colours, optional number box). Written as a frame (setup JSON in `com.cdp.contentsList`) of one-line text fields; the leader is ". . ." after the title in a one-line-high field, so JasperReports (and the canvas) cut it at the end of the line, no measuring. Rows are edited in Basic Properties; resizing changes the row height. **Fill from my section headings** (`fillContentsList` in `PDFDesigner.vue`, `collectHeadings`) lists every Section Heading (`com.cdp.sectionHeading` on the preset's box) and Sub-heading (`com.cdp.subHeading`) on the normal pages in page order, with the page they print on (following "Count the cover and contents pages"); numbers fit the list (`fitNumber`: "SECTION 1." in a wide column, "1" in a narrow one, "01" in a number box). Lists linked by `continues` (a second column, later contents pages) are filled in turn; rows that don't fit go onto new contents pages with a copy of the list; empty linked lists on later pages are removed. Headings moved by tables growing can change the real page: the panel says to check in Preview PDF. **Numbers** (`autoNumber`, on for new lists and the designs): sections counted 1, 2… in a chosen style (`sectionStyle`: 1 / 1. / 01 / I / A / word + `sectionWord`, e.g. "SECTION 1."), sub-sections (indented rows) counted again under each section (`subStyle`: i, ii / a, b / 1.1 / none); counting carries on across a list's chain (`numberStarts`, used by the canvas, the panel and the generator). Unticking keeps the shown numbers as typed ones.

## Page numbers

Written for non-technical users (about 40–60 years old): the panel (`PaginationProperties.vue`) asks plain questions with the pages always in view, and every choice sits next to what it changes (no "More options"). Use everyday words in it ("part", "pages without a number", never "group", "range", "expression").

1. **Format**: four compact cards showing the real text ("Page 1 of 12", using the design's page count), then **Number style** in one row (1 2 3, i ii iii, I II III, A B C).
2. **Which pages get a number?** A dropdown (Every page / Every page except the first / Every page except the first two / Only some pages) with a one-line explanation of the chosen option under it. "Only some pages" holds **parts** (Part 1: pages 1 to 10), each may have its **own look** (text and number style, "Same as above" by default); with two or more parts, **Numbers in each part** (start again or carry on) follows them; then **pages without a number** ("3, 5, 8-10") and, once there are some, **After a page without a number** (count it or not). Choices show a live example. Parts never overlap (a change that would is refused with a sentence saying why); left-out pages only exist inside parts.
3. **Your pages**: one tile per design page (`report.totalPages`) with what it prints (cover and contents pages named, never numbered); settings past the last page get an amber note explaining it's fine if the report grows, otherwise what to change.

With a cover or contents pages, step 2 starts with **Count the cover and contents pages** (default yes, as in printed reports: the first normal page is page N+1). Unticked, every page variable in the page number's expressions is written less N (`shiftPageNumbers`, in the generator only; the settings stay in normal-page numbers and the canvas shifts its preview the same way). Page numbers are never allowed on the cover or contents pages.

Logic in `utils/paginationPresets.ts`, settings kept as `com.designer.pagination.*` properties (only non-default values; older reports keep the same expressions). Parts are `groups` (`…pagination.groups`, "1-3:slash:romanLower,5-9:pageXofY:"), left-out pages `hidden`, `hiddenNumbering` keep/skip, `groupNumbering` restart/continue, `numberStyle` (`styleNumber` / `styleExpression`: Roman from a list up to 300, letters to ZZ, digits beyond). Everything becomes the field's expression and `printWhenExpression` (evaluated at Master time when any part shows a total); the words "Page"/"of" are English on purpose. On a page without a number nothing is shown, on the canvas or in the PDF. Every case has been checked in a JasperReports fill. Not done yet: page-number settings in the AI assistant's tools.

## Report Data (projects)

All report data comes from **projects** in the backend. Which projects the report uses is chosen in the designer header, next to the report name (`designer/HeaderProjectPicker.vue`: one dropdown with a searchable checklist, several allowed; it shows the project's short code, or "N projects selected"). In the left "Report Data" list (`designer/ReportDataPanel.vue`) the chosen projects appear as **tabs** (logo and short code, full name in the tooltip; they wrap onto more rows; arrow keys move between them; a newly added project opens its tab), and the open tab shows that project's **details** (name, code, logo, description, introduction, client…; `ProjectDetails` in `src/types/dataSource.ts`) and its **tables** (sources). Table rows are never stored in the design (fetched each time); detail values are copied into the design when dropped (below).

- **Chosen projects** live in `ReportProperties.projects` (so undo and saving cover them), written as the report property `com.cdp.projects`. A project still used by a table can't be removed from the list (`countProjectUsage`).
- **Details are copied, never linked**: dragging a detail onto the page puts its current value into an ordinary **Text** element (the logo into an **Image** element, as a fixed picture) and nothing stays connected to the project: no parameters, no marker property, no unlink. The user edits it like any text (double-click) and drags the detail again for a newer value. The drag carries the value (`DataSourceDragPayload` `projectField`), and `applyProjectValue` (`utils/projectFields.ts`) writes it the way typed text is stored. A detail with no value is refused with a message.
- Dropped **onto an existing** Text element (a logo onto an Image element, a text detail onto a Barcode whose type can hold the value), it replaces that element's content and keeps its place, size and look (`fillDroppedProjectValue`, `canTakeProjectField`; the wrong kind, a page number or a value the barcode type can't hold is refused with a message saying why; the element frame turns blue / red while dragging). Dropped on empty space, a new element is made. One undo step either way.

## Data Tables

A table shows rows of a project's backend **source** (Procurement, Materials…). Users drag a source (or one column) from the left "Report Data" list onto a table; there are no expressions or queries in the UI. Rows are never stored in the design: they are fetched each time, for the canvas, the preview and the real report.

- **The setup is the single source of truth**: `TableElement.binding` (`TableDataBinding` in `src/types/dataSource.ts`): project (`projectId`, `projectName`; each table can use a different project), source, columns (key, header text, type, width, total), filters, one sort, row limit, totals, style (`theme` + `look` + `customized`), table name and a unique `datasetName`. A table without a binding is an empty placeholder (header + one row, 3 columns, "Drag table data here").
- **Barcode columns**: in the Configure popup a text column can be shown as Code 128, QR Code or Data Matrix (`TableColumnBinding.barcode`; only types that hold any text, Code 128 values kept to plain characters, so no row can stop the report). The detail cell is a frame with the row style holding the barcode; an empty value prints nothing (barcode4j fails on ""). No size is written (values differ per row): each prints at its natural width, shrunk to fit. Rows become at least 36 px tall on Apply. Canvas and popup preview draw the same (`common/BarcodeCell.vue`).
- **Several tables per report**, each independent: its own `datasetName` (`table_xxxxxx`) and name ("Table N"). Copies get new ones (`ensureUniqueTableDatasets` in `utils/table/tableDocument.ts`, called on paste and load).
- **JRXML** (`utils/jrxml/tableXml.ts`), all derived from the binding when the report is written: one `<subDataset>` per table (fields typed loosely, `java.lang.Number` / `java.lang.Object`, because JSON numbers may arrive as Integer and dates as ISO text; cells format them), total variables, `<jr:table>` with header / totals / detail cells styled by the table's look, a no-data cell, and the binding as JSON in the `com.cdp.table.binding` property. The parser rebuilds the table from that property only and drops the table's own `<subDataset>`. An empty table is written as an empty frame carrying the property. Items below a table get `positionType="Float"` so they move down when it grows.
- **Rows reach the report from the backend**: the designer sends only the JRXML (Preview PDF included). The report server reads each table's `com.cdp.table.binding`, gets the request from the report engine (`tableQuery`, moving dates resolved for the run date) and passes the rows to the table's dataset (`datasetName`). The preview window still fetches rows, only to show them in its side panel.
- **Only in the Detail section** (it grows onto new pages; Title and Summary are not supported); never inside a box. Width: at least `MIN_TABLE_COLUMN_WIDTH` (60) per column, so the column limit follows the table width. Height on the canvas: header + up to 5 sample rows (last one "+N more rows") + totals; the PDF prints every row.
- **Data access** goes only through `services/dataSourceService.ts` (`listProjects`, `getProject`, `listSources`, `getSchema`, `getFacets`, `queryRows`; all under `projects/{id}`, contract in the file header). Until `VITE_DATA_SOURCE_API` is set it uses `src/mocks/` (dummy projects with logos, their sources, and the filter/sort logic the backend will take over); never add filtering elsewhere.
- **Editing** happens only in the Configure popup (`modals/TableConfigModal.vue`; double-click a table, "Edit data", or drop a source; it picks the project, then the source); Apply is one undo step Dropping a different source on a filled table replaces its data (like replacing an image): the popup opens with the new source and says so; the table keeps its name and style. The popup has no style picker (styles live in Table Properties). The popup copies the setup with JSON, not `structuredClone` (it can't copy Vue's reactive objects). The preview window is read-only and links back with "Edit in designer".
- **Filter & sort** (`designer/TableFilterPanel.vue` in the Configure popup) works like a shop's filter panel, no technical words: a category list (Sort, then each column) and its choices. Text columns: tick values, with counts, plus search (`operator: "in"`, `values`). Numbers, amounts and dates: a range with quick picks (round buckets, or one per month) plus Min/Max or From/To (`operator: "between"`, either end optional). Dates also offer moving ranges (This month, Last month, This quarter, This year, Last 30 days: `period` on the filter), so a report reused next month shows next month's data; `resolveFilterDates` turns them into dates inside `dataSourceService` before every request (a backend running a saved report must do the same). Filters on different columns all apply; ticked values of one column match any. Only one sort at a time, named for the column type ("Low to high", "A to Z", "Newest first"). Choices come from `getFacets(sourceId)` (backend `GET sources/{id}/facets`; mock `columnFacets`). Filters and sorts carry `label`/`type` for summaries (`utils/table/summary.ts`).
- **Table styles** (`utils/table/tableThemes.ts`) are the only styles in the designer. There are no general report styles, Style Management, Style Reference or Parent Style; imported `<style>`s and elements' `style` attributes are dropped.
  - Built-in styles None (no colours, nothing bold, thin black lines; what Reset style gives a table), Corporate Blue, Minimal, Emerald (`BUILTIN_LOOKS`) are fixed. New tables start in Corporate Blue.
  - A look is a `TableLook` (header/rows/totals colours and bold, **row colours** = 1 to 4 colours the body rows take in turn (`rowColors`, `rowColorAt`; older looks with `rowBackground` + `stripe` are read into it by `normalizeLook`), lines grid/rows/none, line and header-line colours, text size). Typed tables use the same styles (below). Each table carries its own: `binding.theme` = the style it started from (built-in id or saved id), `binding.look` = its actual look (empty for an unchanged built-in), `binding.customized` = changed for this table only. Canvas, popup, preview and JRXML all read `resolveLook(binding)`, so they need nothing else.
  - Table properties follow the Box pattern (`TableDataPanel.vue`, `part` prop): **Basic Properties** = position & size, Data (name, source, filters, Edit data), Look (style tiles, saved-style rename/delete, "changed" note with Reset, Customize button that opens Style Settings), row sizes; **Style Settings** = the Customize editor and Save / Update as table style. Customize changes only that table. "Save as table style" turns its look into a `SavedTableStyle` in the report (`tableStyles` in `PDFDesigner.vue`, written as the report property `com.cdp.tableStyles`); "Update (style name)" overwrites the saved style and every table using it unchanged. Deleting a saved style keeps its tables' look as their own changes. Styles are managed only in the table's properties (no list in the left panel): the style tiles (built-ins locked), and for a table on a saved style a bar to rename or delete that style.
  - JRXML: three report styles per look (`buildLookStyles`; header, row with each extra row colour as a conditional style on `(REPORT_COUNT - 1) % n`, totals): `Table_None_*`, `Table_CorporateBlue_*` etc. for built-ins, `TableStyle_<id>_*` for saved styles, `Table_<datasetName>_*` for customised tables (`tableStylePrefix`, `tableReportStyles`).

## Custom Tables

One **Table** tile, two kinds of content. Clicking the tile asks "What goes in the table?" (like Chart / Barcode): **Type my own** adds a typed table (`customTable`, shown as "Table" too, no tile of its own) in the last clicked band, open for typing; **Use project data** opens the setup popup, which adds the data table (`table`) in Detail on Apply. Dragging the tile drops the empty project-data table. Double-click: a project-data table opens its setup popup, a typed table opens for typing. The same two names switch an existing table at the top of its Basic Properties ("Table content"): project data → typed keeps what the table shows (headings, the rows that fit on the page with a message for the rest, totals worked out from the printed rows, colours); typed → project data asks first, then opens the setup popup (Detail only). One undo step either way (`utils/table/tableConversion.ts`, `addTable` / `convertTableToTyped` / `convertTableToData` in `PDFDesigner.vue`).

A **custom table** is a grid the user types into: no project data. Made for the hand-typed tables of a monthly project report (key statistics, financial summaries, risk registers).

- **The setup is the table**: `CustomTableElement.table` (`CustomTableData` in `src/types/index.ts`): column widths, rows (design height + cells), its table style (`theme` / `look` / `customized`, exactly like a data table's binding, chosen and customised in the same `TableDataPanel` sections, saved styles shared), `headerRows` (0–3) and `totalRow`, space inside cells. A cell has its text (plain, `\n` for new lines; or HTML when `rich`: typed with formatting, written with `markup="html"`), `colSpan` / `rowSpan`, and optional exceptions to the style (fill, text colour, bold / italic / underline, alignment, text size). How a cell looks = the style for its row (header rows, body rows taking the row colours in turn, total row) + its exceptions: `resolveCell` / `cellPens` in `utils/customTable.ts`, used by the canvas and the JRXML alike. New rows have no exceptions (they follow the pattern); new columns copy their neighbour's alignment. A merged cell is the top-left cell of its block; the cells it covers stay in the grid but are not shown or written. All helpers (merge, split, insert / delete rows and columns keeping merges and header rows right, selection grown to whole merged cells, scaling, `normalizeCustomTable`) are in `utils/customTable.ts`.
- **Editing on the canvas** (`elements/CustomTableElement.vue`): double-click (or "Type in the table") opens it; click a cell to type, drag or Shift+click to choose several, arrows move, Tab goes to the next cell, Delete clears, Esc or a click elsewhere on the page closes it. Right-click: insert row above / below, column left / right, delete rows / columns, merge, split, clear. Column and row edges can be dragged. Rows grow on the canvas to fit their text (as in the PDF). The chosen cells are `tableCells` in the selection store, shared with the panel.
- **Properties** (`properties/CustomTableProperties.vue` + the style sections of `TableDataPanel.vue`): Basic = rows / columns / header rows counters, "Last row is a total", the look of the chosen cells (all cells when the table isn't open; shows the real look, sets only what differs from the style, ↺ returns to the style's colours), merge / split, then the table style tiles; Style Settings = the table style editor (row colours 1–4 included) and space inside cells. One undo step per action.
- **JRXML** (`utils/jrxml/customTableXml.ts`): JasperReports' table can't merge down, so a custom table is plain frames and text fields written straight into its section, with no frame around the whole table (a frame that is pushed down and then split over a page gets blank space at its end on the next page). One frame per row (`positionType="Float"`, cells `textAdjust="StretchHeight"` + `stretchType="ContainerHeight"`), so a row grows to its tallest cell and rows below move down; rows tied by a merged-down cell are one block frame (row frames inside, the last one `ContainerBottom`, merged cells over them). The first frame carries the table's uuid and the setup JSON (`com.cdp.customTable`), the others `com.cdp.customTable.part`; the parser rebuilds the table from the setup and skips the parts. Items below a custom table float, like below a data table. A long table splits over pages; no repeated header row (yet). Not allowed inside a box.
- **Typing in a cell** uses an editable box with the same formatting toolbar as text (`TextFormatToolbar`); on closing, the cell is kept as plain text unless it has formatting (`readEditor`; `hasFormatting` / `cleanEditorHtml` in `utils/elementUtils.ts`, shared with text elements). Merging a plain and a formatted cell keeps the formatting.
- **Reset style** (Style Settings, top right, and the right-click menu; `utils/resetStyle.ts`) on any element: removes colours, borders, fonts, shapes and corners, keeps content, place and size, one undo step (several selected items: one step). A box keeps its parts, a page border keeps a plain border, a page number keeps its side. Tables (both kinds) get the None style (only their lines); a typed table also loses its cell exceptions but keeps text, merges, header rows and sizes.
- Project data → typed keeps at most the first 10 rows (`CONVERTED_ROW_LIMIT`), fewer when they don't fit on the page.
- A table taller than the page can't be designed on one page (JasperReports needs every section to fit the page); split it into two tables on two pages.

## Charts

One **Chart** element with nine types (KPI Stat, Gauge, Line, Area, Bar, Horizontal Bar, Pie, Donut, Tree Map; `utils/chart/chartTypes.ts`), the same set as the CDP app's dashboards. It works like Page Number: clicking the library tile asks for the type (grouped: Track one number, Show a trend, Compare categories, Part of a whole), dragging it drops a bar chart, and Basic Properties changes the type.

- **The setup is the chart**: `ChartElement.binding` (`ChartBinding` in `src/types/dataSource.ts`): type, title, legend, colour set, and its data: project and source, the number shown (`measure`: count, or total / average / lowest / highest of a number column), categories (`dimension`; dates grouped by day…year), the tree map's `level2`, the lines or bars (`series`, each optionally one per value of a text column), `stacked`, `limit` (largest N text categories, the rest added up as "Other" for counts and totals), `gaugeMax`, `filters` (the table filters). `normalizeChartBinding` reads any stored value safely; `isChartComplete` says whether the type has everything it needs; `changeChartType` keeps the data when the type changes.
- **Numbers are never stored**: charts use the CDP backend's analytics endpoint, exactly as the CDP app's dashboards do (cdp-fe-app `aggregate.api.ts`): `POST {VITE_OAUTH_BASE_URL}/v2/analytics/aggregate` with the user's login, body `AggregateRequest` (`entityName` from the source's schema, `measure` `{ aggregation: "SUM", property }`, `dimension` `{ property, granularity: "MONTH" }`, `splitBy` `{ property }`, the chart's filters as a Jmix `filter`, and `globalFilter` `project.id = projectId`), answer `AggregateResult` (rows / series with `key`, `label`, `value`, `count`; `totalValue`, `totalCount`, `truncated`; an `{ data, message, status }` wrapper is unwrapped). `chartRequests()` (`chartQuery.ts`) builds one request per series (the binding keeps lowercase names; only the request uses the CDP ones); `aggregate()` in `dataSourceService.ts` sends it, or answers it from the dummy rows (`aggregateRows`) while Report Data is dummy data; `mergeChartData()` puts the answers in order (dates by time with empty buckets filled, text by size), labels them and adds "Other". Answers are cached for the session by request (`chartDataStore.ts`, cleared by the Report Data refresh button); the canvas asks for them, and Preview PDF / Download wait for every chart first (`ensureChartData`). When numbers arrive, `chartDataVersion` makes the designer rewrite the JRXML.
- **States** (`chartView`, `chartImage.ts`): not linked → sample numbers, faded, "Sample data" badge; linked but unfinished, loading, or failed → the same with a badge saying so; ready → real numbers. Only ready charts print; the others are written with an empty image and print nothing.
- **Data setup** happens in the Configure popup (`modals/ChartConfigModal.vue`; double-click the chart, "Set up data" / "Edit data" in Basic Properties, or drop a source or column from Report Data onto it, which opens the popup with that source). It picks the type, project, source, what to show and the filters (`TableFilterPanel` without Sort), with a live preview at the chart's size; Apply is one undo step. A new source gets sensible defaults (a date column for charts over time, otherwise the text column with the fewest different values). Series measuring different things (a count next to amounts) get a second scale.
- **One look for canvas and PDF**: `buildChartOption()` (`chartOption.ts`) turns setup + numbers into ECharts settings laid out for print (no animation or tooltips). The canvas draws them live; `chartImageDataUri()` (`chartImage.ts`) renders the same settings to SVG. ECharts is imported from `echarts/core` with the SVG renderer only (`echartsSetup.ts`).
- **JRXML**: a chart is an `<image>` whose expression is an SVG data URI and whose `com.cdp.chart.binding` property holds the setup. The parser rebuilds the chart from the property and ignores the picture. The report server already prints data-URI images (`processImageElement`), SVG as vector graphics through Batik. ECharts' `<style>` block (hover rules only) is removed from the SVG because Batik fails on it.
- **Colours never repeat**: `chartColors(palette, count)` (`chartTypes.ts`) gives the colour set's own colours, then generates new distinct ones in the same style (shades of grey for the grey set), as many as the chart needs: one per slice, tree map group, series, or, for bar charts with one series, one per bar (their legend is hidden; the axis names the bars).
- **The report server redraws charts**: the designer sends only the JRXML. The server runs the report engine (below) in GraalJS: `chartRequests` → it calls the analytics endpoint → `chartSvg` → fresh picture. The picture the designer writes stays as the fallback when that fails.
- Charts go in any band and inside boxes (a fixed-size image never grows). Charts are never uploaded to S3: the picture is redrawn from the setup every time. A project used by a chart can't be removed from the report (`countProjectUsage`), and the Report Data list names the charts using each source.

## Report engine (charts and tables on the server)

`src/engine/reportEngine.ts`, built by `npm run build:engine` into `dist-engine/cdp-report-engine.js` (one IIFE, global `CdpReportEngine`), runs the designer's own chart and table code in the report server's GraalJS, so the server builds the same requests and the same chart pictures from the JRXML alone. Functions (strings in, strings out): `chartRequests(binding, today)`, `chartSvg(binding, results, width, height, locale)`, `tableQuery(binding, today)`; `ENGINE_VERSION` is bumped when they change. Contract and Java usage: `docs/REPORT_ENGINE.md`.

- **Code the engine bundles must not use the browser or Vue**: `utils/chart/chartTypes`, `chartData`, `chartQuery`, `chartOption`, `chartSvg`, `chartText`, `echartsSetup`, `utils/table/dataBinding`, `tableThemes`, `config/fonts.config` (no `window`, `document`, storage, `btoa`, Pinia, vue-i18n, services). Chart texts go through `chartT` / `chartLocaleTag` (`chartText.ts`): `main.ts` plugs in vue-i18n, the engine uses the `chart` part of the locale files. Browser-only chart code (the data store, the canvas, `chartImage.ts`) stays outside the engine.
- `src/engine/globals.ts` gives ECharts the do-nothing timers a bare JS engine lacks.
- After changing chart or table code: `npm run build:engine`, check the file still runs without a browser (a bare `node:vm` context), and hand the new file to the backend.

## Barcodes

One **Barcode** element (`<componentElement>` with a JasperReports barcode component: barcode4j, QR Code by zxing). Like Chart, clicking the library tile asks for the type (cards with a drawn sample, grouped: Products in shops, Labels/stock/shipping, 2D codes, Post); dragging it drops a Code 128. Basic Properties shows the same cards (styled like the image Shape presets) and the value.

- **Types, samples, examples, default box sizes and input rules** live in `utils/barcode/barcodeTypes.ts`. The rules copy barcode4j 2.1 (checked against the jar, UPC-E check digit on the number written out as UPC-A), because a value the type can't hold stops the whole report. Each type keeps its own value (`switchBarcodeType`): switching shows the value typed for that type before, or its sample, never the previous type's value; the other types' values are kept in `valuesByType`, written as the `com.cdp.barcode.values` property. Switching to another kind (bars, square, PDF417, postal) gives that kind's box size, in the same undo step. Plain text is stored as a Java string literal (`toBarcodeExpression`); only `$F{` / `$P{` / `$V{` values are expressions.
- **Filling the value**: every type lists clickable examples (`BARCODE_EXAMPLES`, each with what it is). EAN/UPC show the check digit (added when printed, or confirmed when typed). QR codes get a form (`QrContentEditor.vue`, `utils/barcode/qrContent.ts`): web link, text, email, phone, text message, Wi-Fi, contact card, written in the formats phone cameras read (`https://`, `mailto:`, `tel:`, `SMSTO:`, `WIFI:`, vCard); the kind is read back from the value, nothing extra is stored. GS1-128 gets a field builder (`Gs1Editor.vue`, `utils/barcode/gs1.ts`: item number, batch, expiry…, "ñ" after a variable-length field that isn't last, item number check digit added); values with codes it doesn't know are edited as text. A project detail can be dropped onto a barcode (below).
- **A barcode fills its box, like an image** (`utils/barcode/barcodeImage.ts`): `barcodeSizing` turns the box size into attributes on the barcode component (`moduleWidth` + `quietZone` for 1D codes, columns and module width for PDF417, bar/gap widths and bar heights for postal codes) so JasperReports draws it as wide and tall as the box; the canvas draws with the same numbers (`barcodePicture`, bwip-js for the bars, 8pt text laid out like barcode4j). A QR code is centred in the box, Data Matrix top left and always square (`shape="force-square"`). Barcodes are written `mode="Transparent"` (JasperReports paints them white otherwise). Code 128, GS1-128 and PDF417 need bwip-js to be sized: the designer rewrites the JRXML when it has loaded, and Preview PDF / Download wait for it (`ensureBarcodeLibrary`). The panel warns when the bars get too thin to scan. An expression or a value that doesn't fit is drawn as a faded sample with a badge.
- **Rotation**: JasperReports' barcode `orientation` 90 = left, 270 = right. A QR code has no `orientation` in the schema (JasperReports rejects it), so it is never written, the rotation control is hidden and switching to QR resets it.

## No tests in this repo

The repo has no test framework and no test files, on purpose. **Never add test files, test folders, test config or test packages** (Vitest, Jest, jsdom, @vue/test-utils…).

**Keep the JRXML validation tools**: Validate XSD / Auto Fix / Preview PDF in the app, `tools/`, `validator/`, `test-attribute-validation/`, and the scripts and sample reports in `tests/` (`jrxml-compatibility-test.ts`, `test_autofix.spec.ts` + its `.jrxml` files, `preview-server-test.html`). They are standalone checkers, not a test framework. Never delete them as "test files". How to run them: `docs/VALIDATION.md`. JRXML element order and attributes: `docs/JRXML_REFERENCE.md`.

To check a change, verify it with a throwaway script in the session scratchpad (outside the repo) and delete it once done. Run it with plain Node/`tsx`, or for the JasperReports engine check use the compile-and-fill harness with the jars in `~/.m2`. If a quick check really must sit inside `src/` (for the `@/` imports), delete it in the same session and make sure `git status` shows nothing left behind. Then confirm in the app itself.

### JRXML must stay valid: check it after every change

Any change to the generator, the parser, an element, a template, a style or a table must be checked for broken JRXML before it is called done. One stray `<`, `&`, quote or `]]>` and the report server rejects the whole report (`SAXParseException … The content of elements must consist of well-formed character data or markup`), so the preview and the real report both fail.

1. Every value the generator writes goes through `xmlAttr()` (attribute values) or `cdata()` (expressions) from `src/utils/jrxml/xmlEscape.ts`. Never write `="${value}"` or `<![CDATA[${value}]]>` directly.
2. With a throwaway script (see above), build a report that uses what you changed, with awkward text (`<`, `&`, quotes, `]]>`) in every place a user can type. Check it with a strict XML parser as generated, after a save and reload (`parseJRXMLContent` → `generateJRXMLContent`) and after `formatXml()`. Then delete the script.
3. In the app: JRXML Content → **Validate XSD**, then **Preview PDF**. Both must succeed.

The JRXML panel shows, validates, previews and saves the *formatted* text, so formatting must never change the report: use `formatXml()` (`src/utils/jrxml/formatXml.ts`, whitespace between tags only). Never use an HTML beautifier (`html_beautify` rewrote `<![CDATA[` into `< ![CDATA[` and `$V{` into `$V {`, which broke every report).

## Key Conventions

- TypeScript strict mode
- Vue 3 `<script setup>` composition API
- State management: **Pinia** (registered in `main.ts`, stores in `src/stores/`, setup-style `defineStore`):
  - `useReportStore` (`report.ts`): the whole report (page settings, bands and elements, page count, fields, parameters, sub-datasets, saved table styles, variables, groups), the JRXML and its writer `updateJrxml()`, page size / page count / band list getters, fitting Detail to the page, turning bands on or off (`setBandTypes`), and undo/redo over all of it (`saveStateToHistory` before every change). **Every way of opening a report goes through `loadReport()`**, which sets every part (missing ones get their new-report value), repairs shared IDs, clears the selection and starts an empty history (`keepHistory` when applying edited JRXML, which is one undo step). Never assign the report fields one by one to open a report.
  - `useSelectionStore` (`selection.ts`): selected band and element(s), the element being edited, the last clicked band (where library elements go; none yet: Detail) and the last clicked / worked-on page (`lastClickedPageIndex`: a Detail element added by clicking a tile goes on that page, else the first normal page; a Contents List prefers a contents page; `placeOnPage` in `PDFDesigner.vue`).
  - `useEditorStore` (`editor.ts`): zoom, snap/grid toggles (remembered per browser), alignment guides, drag/resize in progress, keyboard focus on the page area, panel layout.
  - `useFilesStore` (`files.ts`): the reports saved in this browser, the open file (name, id) and its save status; `useDesignerFiles` reads and writes browser storage around it.
  - `PDFDesigner.vue` resets them when it opens. The canvas, `ElementProperties`, `BottomPanel`, `ElementLibrary` and `FileManager` read the stores directly; property panels and canvas elements call `saveStateToHistory()` / `updateJrxml()` themselves. Auto-save stays in the designer (it saves when the store writes a new JRXML, `jrxmlVersion`).
  - Not in stores, on purpose: temporary interaction state in `PDFDesigner.vue` (drag preview, drop highlight, context menu, open popups, clipboard), caches (chart data, table rows, the barcode library), and drafts local to one input. New shared state goes in a store, never in module-level refs or prop chains.
- i18n via vue-i18n: English (`en`, default) and Malay (`ms`); all text outside `src/locales/ms.json` is English; locale files in `src/locales/`, choice stored in localStorage (`appLocale`)
- User-visible text always goes through a translation key; never hard-code UI text
- Locale files stay in sync: whenever a key is added, changed, renamed or deleted in `src/locales/en.json`, make the same change in every other locale file (currently `ms.json`) in the same edit, with a real translation, not English copied over
- **Text formatting** (text elements and custom table cells, `TextFormatToolbar.vue`, shown when text is selected): bold, italic, underline, strikethrough, **superscript / subscript** (`<sup>` / `<sub>`), **bullet and numbered points** (`<ul>` / `<ol>` / `<li>`: select the lines, click the button; Enter adds the next point, Enter on an empty point or Shift+Enter ends it), colour, highlight, link. All of it is JasperReports `html` markup, checked in a fill; JasperReports indents each list level by a fixed 50pt, and the canvas CSS does the same.
- **Look**: one theme for the home page and the designer: Naive UI `themeOverrides` in `App.vue` (primary #6440F4, borders #E6E5EE, text #1C1B26, 8px corners) and the same values in the `--prop-*` tokens (`styles/properties-panel.css`). Use the purple, never the old blue (#1890ff). Property sections are white cards (1px border, 10px corners, soft shadow); the Element Library is cards with a responsive tile grid.
- **Narrow-window menu** (☰ next to the logo, `designer/HeaderMoreMenu.vue`): shown only when the header hides tools (`headerTier >= 3`), and holds just the hidden ones, grouped as Edit / Pages / View / Export. ⋯ is used only for page and element menus.
- **Side panels** (Element Library left, Properties / AI right; `panels/ResizablePanel.vue`): dragged by an 8px strip on their inner edge (pointer captured, so moves over the canvas or outside the window still count), between `LEFT_PANEL_MIN/MAX_WIDTH` / `PROPERTY_PANEL_MIN/MAX_WIDTH` and never wider than their share of the window (`*_WINDOW_SHARE`, `maxWindowShare` prop; a narrow window shows them narrower, the stored width comes back when it widens); the canvas takes the rest. Widths remembered per browser (`designer.leftPanelWidth`, `designer.rightPanelWidth`).
- **Bottom panel** height: drag up to the header's bottom edge (measured), snaps at 1/3, 1/2 and full; Maximize / Restore button and double-click on its top edge (an 8px grab strip with a grip, above the panel's sticky tab row); height remembered per browser (`designer.bottomPanelHeight`).
- **Motion**: folds (library categories, Report Data tables, the bottom panel shown / hidden) use `common/Collapse.vue` (height + fade, restores the element's own inline size afterwards); side panels never animate their width (the canvas would be laid out on every frame and flicker): the layout changes in one step, the panel's content is revealed / clipped back from its edge (`clip-path`, `ResizablePanel` `revealContent` / `hideContent`) and the canvas glides from its old place with a transform (`glideCanvas` in `PDFDesigner.vue`), both with `PANEL_MOTION` (`constants.ts`); menus use the `menu-pop` transition, popups `modal-pop` (in `BaseModal`), both in `src/style.css` with the page / tab / card fade-ins. `ResizablePanel` glides on the bottom panel's maximize / restore but never while dragging (`is-resizing`). Everything is off under `prefers-reduced-motion`; dragging, resizing and zooming stay instant.
- The designer header logo links to the reports home (`home` route, tooltip "Reports home").
- Colour inputs use `src/components/common/ColorSwatchPicker.vue` (Naive UI picker whose popover stays inside the window), not `<input type="color">`, whose native popup can open off-screen. Exception: the inline text toolbar (`TextFormatToolbar.vue`) keeps native inputs, because focus moving into a page popover would drop the text selection being formatted.
- Multi-select fields (e.g. the Report Data projects) use `@vueform/multiselect` (`mode="tags"`, its `themes/default.css` restyled with `--ms-*` variables); its built-in icons are replaced through the `tag`, `option`, `caret` and `spinner` slots with Lucide icons
- **Icons come from `@lucide/vue` only** (`import { Trash2 } from "@lucide/vue"`, sized with `:size` / `:stroke-width`). Never add hand-written inline `<svg>` icons, `h("svg")` render functions, SVG strings with `v-html`, SVG `data:` URIs in CSS, icon image files, or emoji / Unicode glyphs used as icons (✕ ▶ ⚠ 🤖 …). Element library icons are Lucide components in `ElementRegistry.ts` (`iconComponent`); plain-DOM code mounts them with Vue `render(h(Icon), el)` (see `utils/notification.ts`). Native `<option>` text can't hold icons, so leave options as plain text. If no Lucide icon fits, suggest the closest Lucide candidates to the user and let them choose instead of drawing one. Decorative shapes are plain CSS. Inline `<svg>` is only for drawing report content: lines (`LineElement.vue`, `jrxmlHtmlRenderer.ts`) and the canvas grid
- Default report font: Noto Sans SC (`DEFAULT_REPORT_FONT` in `src/config/fonts.config.ts`), the only font the report server has. Font pickers offer only `SUPPORTED_FONTS` (read-only with an info note while there is one); `resolveReportFont()` maps any other stored font to the default on the canvas and in the JRXML. `SYSTEM_FONTS` is kept for when more fonts are supported
- JRXML namespace: `http://jasperreports.sourceforge.net/jasperreports`
- Element UUIDs required by JasperReports XSD
- **Styles** (`<style>`) are written only for tables and follow the JasperReports schema: font and alignment are attributes (`fontName`, `fontSize`, `isBold`, `hTextAlign`, `vTextAlign`), and conditions only appear inside `<conditionalStyle>` (with a nested `<style>`). No parent styles, no `style` attribute on other elements.
- **Undo/redo** (`useReportStore`, built on `src/composables/useUndoRedo.ts`) snapshots the whole model (bands, fields, parameters, sub-datasets, saved table styles). Every editor change must take a snapshot **before** mutating: `saveStateToHistory()` from the report store (`useReportStore`, in `PDFDesigner.vue` and the property panels), then `updateJrxml()` after. One user action = one undo step: record once per action (not once per side or per keystroke; see `recordBorderEdit` in `ElementProperties.vue`), and for drags/resizes record at the start, not on mouse-up. New features must be checked with Ctrl+Z / Ctrl+Y.
